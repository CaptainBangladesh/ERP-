# Map — Marketing Automation

Label: wayfinder:map

## Destination

A complete, enterprise-grade **Marketing Automation** module (`marketing`, Core/Growth tier, `dependsOn: ['crm', 'parties']`) delivering:
1. **Multi-Network Social Media Suite (Metricool-style)**: Visual drag-and-drop calendar, single multi-network composer (Instagram, Facebook, TikTok, LinkedIn, YouTube, X, Pinterest, Threads, Bluesky, Google Business Profile), platform-specific formatting, autolists/evergreen recycling queues, centralized social inbox for comments & DMs, and keyword-triggered DM automation flows.
2. **Campaign Management & Attribution**: Campaign budgeting, target audience segmentation, UTM link generation, SmartLinks (Link-in-Bio pages with shoppable grid mirrors), and cross-network paid ad performance sync (Meta, Google, TikTok Ads).
3. **Inbound Lead Generation & Nurturing**: Custom web forms, ad lead sync webhooks, drip email sequences, and automated lead scoring that emits `marketing.lead.captured` / `marketing.lead.qualified` to seamlessly create and promote `Lead` records in the `crm` module.
4. **Web Tracking & Analytics**: Proprietary JavaScript tracking pixel for real-time page views, visitor attribution, and campaign conversion reporting.
5. **Brand Multi-Tenancy & Governance**: Brand workspace isolation, AES-256 encrypted OAuth token vault, client review/approval links, and white-label automated PDF/PPT reporting.

Settled architecture decisions locked during chartering:
- **Dedicated Module Boundary**: Lives in `backend/src/modules/marketing`, preserving `crm`'s focus on sales pipelines and emitting decoupled domain events for lead conversion.
- **Postgres-Backed Queue with Swappable Adapter**: Uses an `IJobQueue` port implemented with Prisma and partial indexes for zero new infrastructure dependencies, swappable for BullMQ/Redis if high scale requires it. *(Resolved in ticket 12 per decision 12.1d: the claim is **atomic conditional `updateMany` claims, `batchSize * 2` over-fetch, one round-trip per candidate** — not `FOR UPDATE SKIP LOCKED`, which the code never had. Correct under READ COMMITTED; real `SKIP LOCKED` would need a `$queryRaw` exemption from ADR 0003 and buys correctness nothing at this volume. The round-trip cost and the trigger for revisiting are commented at `poll()`.)*
- **Direct Cloud Media Uploads**: Client uploads media directly to object storage via pre-signed URLs, preventing video/asset transcoding from exhausting application server memory.
- **Brand-Scoped Encrypted OAuth Vault**: Tokens for connected networks are encrypted at rest with AES-256 and scoped to Brands, allowing multiple team members to manage accounts safely.

### Ticket 11 — design pass (2026-09-07, decisions only; no code written)

Classifier (`./scripts/classify-ticket.sh`) returned 3 strong signals — public/unauthenticated
surface, credentials & secrets, redirect/external link — and recommended an Opus design pass
before implementation. These are the rules implementation must follow. Where a rule conflicts
with an existing test, the code is wrong, not the test.

- **11.1 Route contract — the fix is the segment, not the ordering.** Move the ticket-01 scaffold CRUD to `@Controller('api/marketing/records')` and update `MARKETING_ROUTE` / `MARKETING_PATHS` in `packages/src/modules/marketing/contract.ts` plus the "Campaign Records" tab; do not merely reorder `marketing.module.ts:57`. Reason: reordering makes the eight list routes work today while leaving the next sibling route added to the module silently shadowed. **Rule:** no controller mounted at a module root may declare a bare `:id` parameter at path depth 1 — dynamic segments must sit under a literal noun segment (`/records/:id`, `/brands/:id`). Enforce as conformance rule `no-bare-id-at-module-root` in the pack (ADR 0005: boundaries are enforced mechanically, not by discipline), and ship the eight-route HTTP smoke test in the same commit so the router is exercised for real rather than through MSW.

- **11.2a Bio-page theme — validate per key, reject, never sanitise.** `theme` stops being `optional(jsonObject(...))` and becomes a closed typed schema. Reason: the `<style>` interpolation at `smart-links.service.ts:380-383` is only safe if the value could not have contained a delimiter in the first place; escaping inside a CSS context is a second-class defence and was already forgotten once. **Rule:** `primaryColor` and every other colour key must match `/^#[0-9a-f]{3,8}$/i`; `fontFamily` must be one of a hard-coded allowlist of font-stack identifiers (never a free string, never interpolated as a quoted CSS string); `cardStyle` must be a member of its existing union. Unknown keys are rejected. A failing theme returns **400 at write time** — never a stripped/coerced value, never a fallback render. No user-controlled value is ever interpolated into a `<style>` block, an inline `style=` attribute, or a `<script>` block anywhere on the public page.

- **11.2b Link fields — allowlist the URL scheme at write time.** `buttonLinks`, `shoppableGrid` and `socialLinks` become properly typed arrays instead of `jsonArray(...)`, and every URL-bearing field is validated on the write path. Reason: `escapeHtml` (`:588`) makes a `javascript:` href *inert-looking* and still fully executable, which is exactly the case OWASP calls out. **Rule:** parse with `new URL(value)` and accept only `https:`, `http:`, `mailto:`, `tel:` — anything else (including `javascript:`, `data:`, `vbscript:`, protocol-relative `//host`, and any value that fails to parse) is a 400. Validation lives in the schema at the write boundary, not in the renderer; the renderer may assume validated input but must still escape. Re-validate on the read path only as an assertion that throws in dev and drops the single link in prod — never as the primary control.

- **11.2c The public renderer must not be able to 500.** Reason: `escapeHtml` throws on a non-string, so one legacy JSON row makes `/b/:slug` unavailable, and legacy rows exist precisely because these columns were never typed. **Rule:** `escapeHtml` coerces defensively (`String(value ?? '')`) and never throws; the bio-page render path treats every persisted JSON value as untrusted and unshaped, skipping any entry that does not match the expected shape rather than aborting the page. A malformed row degrades one card; it never takes down the page. Cover with a test that seeds a row containing a number, a nested object and a `null` in each JSON array and asserts 200.

- **11.2d Origin isolation — same origin for ticket 11, with a recorded trigger.** Decision: **do not** move `/b/:slug` to `links.<host>` in this ticket; land the validation and CSP now, and treat the origin split as a required prerequisite before bio pages are advertised on a customer-facing custom domain. Reason: the split is the only mitigation that survives a future renderer mistake, but it needs DNS, hosting config and an absolute-URL contract for every asset the page emits — that is an infra change, and blocking the module's only unblocking ticket on it trades a certain functional win for an uncertain infra one. **Rule:** (i) the ERP session cookie must be `HttpOnly`, `Secure`, `SameSite=Lax` and **host-only** (no `Domain=` attribute) — verify this before shipping, because a parent-domain cookie would make the future split worthless; (ii) the bio page renders no ERP session state and issues no authenticated fetches; (iii) the split is carried as an open infra decision under ticket 12's secrets/infra scope, triggered by either a custom domain or the first bio-page feature that needs to embed third-party content.

- **11.2e CSP is defence in depth, ordered behind validation.** Serve `/b/:slug` and `POST /b/:slug/clicks` under a per-response nonce CSP. Reason: it converts a future escaping miss from stored XSS into a blocked console error, but it must never be the reason a bad value is considered acceptable. **Rule:** `default-src 'none'; style-src 'nonce-<n>'; img-src https: data:; script-src 'nonce-<n>'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`. No `unsafe-inline`, no `unsafe-eval`, no wildcard `script-src`. The nonce is generated per request from a CSPRNG. A test must assert the header is present and contains no `unsafe-` token.

- **11.3a Rate limiting — add the throttler, and write down what its storage does not do.** Adopt `@nestjs/throttler` and decide storage explicitly rather than inheriting the default silently. Reason: there is no HTTP rate limiting anywhere in this application, and the in-memory store gives per-instance limits that read as global ones in a review. **Rule:** `ThrottlerModule` registered globally with `@SkipThrottle()` on authenticated internal routes and explicit `@Throttle` on the three public writes — `POST /api/marketing/forms/:formId/submit`, `POST /api/marketing/collect`, `POST /b/:slug/clicks`. Storage: **accept the in-memory store knowingly for phase 1**, since the deploy is currently single-instance and adding Redis contradicts the module's zero-new-infrastructure charter; the limits are therefore *per instance*, and that sentence must appear in the module README next to the numbers. Key by client IP plus the path parameter (`formId` / site / slug) so one abusive form cannot consume another's budget. Exceeding a limit returns **429** with `Retry-After` and no body detail. The moment the app runs more than one instance, throttler storage becomes a blocker — that is the recorded trigger, not a nice-to-have.

- **11.3b Form submissions — the declared schema becomes the actual contract.** `forms.service.ts:221` must validate the incoming `fields` against the form's own `schemaFields` before anything is written. Reason: today the declared shape is decorative and `fields.email as string` is a cast, so an object reaches a Prisma string column and returns 500 on a public endpoint — an unauthenticated caller can pick the status code. **Rule:** every submitted key must exist in `schemaFields`; unknown keys are dropped (not rejected — forms get edited and in-flight pages lag); missing required fields and type mismatches return **400** with a field-level message and no stack detail. Contact fields extracted for the CRM (`email`, `phone`, `name`) must be type-checked as strings and format-checked before extraction, never cast. Additionally: a honeypot field that must be empty, and a per-form daily submission cap enforced in the same transaction as the counter. ADR 0012 behaviour — a public submission fills empty fields only, never overwrites — stays exactly as it is.

- **11.3c The submit path is one transaction.** The submission row, the counter increment and the CRM `Lead` create/update move inside a single `prisma.$transaction`. Reason: they are written separately today, so a failure after the lead is created leaves an orphaned lead in the sales pipeline with no submission to explain it. **Rule:** all three writes commit or none do; the `marketing.lead.captured` domain event is emitted **after** the transaction commits, never inside it, so a rollback cannot publish a phantom event. If the CRM bridge fails, the whole submission fails and nothing is persisted.

- **11.4a Credential storage and masking — mask the plaintext, never the ciphertext.** `social-accounts.service.ts:404` currently calls `maskToken(row.encryptedAccessToken)`, so the UI shows the last four characters of a GCM auth tag. Reason: it is meaningless to the user and it leaks a fragment of the authentication tag, and two of the four failing vault tests are reporting exactly this. **Rule:** ciphertext (`encryptedAccessToken`, `encryptedRefreshToken`, IV, auth tag) never leaves the service layer — not in a DTO, not in a log line, not in an error message. Masking is computed by decrypting inside the service and returning `••••` plus the last four characters of the **plaintext** token; the decrypted value exists only within that call frame. The masking assertions in `backend/test/marketing-vault.spec.ts` are correct as written and **must pass without being edited**. Add a test asserting no controller response body carries a field name matching `/^encrypted/`.

- **11.4b Double publish — claim the row conditionally, never read-then-write.** Replace the read-`post.status`-then-write-`PUBLISHING` pair at `social-publisher.service.ts:129` with the conditional claim the job queue already uses. Reason: two concurrent calls both pass the read and both hit the network, which means a duplicate post on a client's real social account — externally visible and not undoable. **Rule:** `updateMany({ where: { id, status: { in: [<publishable states>] } }, data: { status: 'PUBLISHING' } })` and proceed only when `count === 1`; a `count === 0` is a normal no-op, not an error. No network call may be made before the claim succeeds. This is the same pattern as the queue's claim loop and should read identically, so the module has one concurrency story rather than two. Test: two concurrent publishes of one post produce exactly one adapter call.

- **11.4c Quota is counted at publish time, on published posts.** `social-publisher.service.ts:492` and `social-accounts.service.ts:469` must both count by actual publish timestamp, not `createdAt`, and must not treat `SCHEDULED` as spent. Reason: counting creation time blocks today when 60 posts are bulk-scheduled for next month, and blows Meta's real 50/24h limit when 50 posts scheduled last week fire today — the guard fires in exactly the wrong two cases, and the number shown in the UI is decorative. **Rule:** the rolling window counts rows with `status = 'PUBLISHED'` and `publishedAt >= now - window`; a `FAILED` attempt that reached the network **does** count (the platform counted it), one that failed before the network call does not — record which rather than inferring. Both call sites read the count from one shared helper so the displayed number and the enforced number cannot diverge again. Delete the shim `if (typeof this.prisma.scheduledPost?.count !== 'function') return;` outright — a production limit must never be disableable by the shape of an injected mock; tests that relied on it get a real stub instead.

### Ticket 12 — design pass (2026-09-07, decisions only; no code written)

Classifier (`./scripts/classify-ticket.sh`) returned 2 strong signals — credentials & secrets,
hard reasoning (concurrency/correctness) — plus a weak third-party/validation signal, and
recommended an Opus design pass first. Decisions below are binding on implementation. Where a
rule conflicts with an existing test, the code is wrong, not the test.

- **12.1a Lease reclaim — the reaper runs inside the poll tick, and reclaims by clock only.** Add a janitor pass at the top of `poll()`, inside the same `withoutCompanyScope` block, moving rows with `status = 'PROCESSING' AND lockedAt < now() - LEASE` back to `PENDING` when `attempts < maxAttempts`, and to `FAILED` with a `lease expired` error otherwise. Reason: a dead worker currently strands a job in `PROCESSING` forever, and for a scheduled-posting product that means posts silently never go out while the dashboard stays green — the worst defect in the module. **Rule:** the lease is a single named constant (`JOB_LEASE_MS`, 5 minutes) exported from `postgres-job-queue.service.ts` and compared against `lockedAt` only — never `updatedAt`, never a heartbeat the worker has to remember to send. The reclaim is one `updateMany` per terminal state, not a read-then-write loop. The janitor must **not** reset `attempts`: an expired lease is a spent attempt, otherwise a job that reliably kills its worker retries forever.

- **12.1b Fencing — `attempts` is the fence token, and `complete()`/`fail()` take it as a parameter.** Reason: a lease alone makes things worse, not better — a slow-but-alive worker outlives its lease, the job is re-claimed, both run, and the stale worker's `complete()` overwrites the re-claimed run's state. The claim already increments `attempts`, so the claimed value is a monotonic token that costs no new column. **Rule:** `poll()` returns the claimed `attempts`; `complete(jobId, attempts)` and `fail(jobId, attempts, ...)` add `attempts` to their `updateMany` `where` alongside `id` and `status: 'PROCESSING'`, and a `count === 0` is a **normal no-op logged at warn** ("stale worker, job re-claimed") — never an exception, never a retry. The signatures change so a caller cannot forget the token: no optional parameter, no default. Do not ship 12.1a without 12.1b in the same commit; the two are one change.

- **12.1c Concurrency — bounded `allSettled`, and the bound is its own constant, not `batchSize`.** Replace the sequential `await` at `job-queue-worker.service.ts:82` with `Promise.allSettled` over a fixed-size window. Reason: ten posts to Meta currently go out one after another, so a batch takes the slowest network call times ten — and the lease is measured against that. **Rule:** `JOB_CONCURRENCY = 5`, kept separate from `batchSize` so raising the poll batch cannot silently raise outbound API pressure; each job keeps its own `tenancy.runInCompany` frame (no shared tenant context across the window); a rejected settle is already handled by that job's `fail()` and must not abort its siblings or the tick. The lease must stay comfortably longer than the worst-case job under this concurrency — that relationship is why both numbers live next to each other with a comment.

- **12.1d The `SKIP LOCKED` claim is a documentation defect — correct the map, do not add raw SQL.** Decision: keep the conditional-`updateMany` claim loop and fix the ticket-03 decision entry above, which describes a `FOR UPDATE SKIP LOCKED` the code never had. Reason: the current claim is genuinely atomic under READ COMMITTED, so this buys correctness nothing; real `SKIP LOCKED` needs `$queryRaw`, which `check:tenancy` fails by design under ADR 0003, and spending this module's first raw-SQL exemption on a performance nicety at current volume is the wrong first exemption. **Rule:** amend the ticket-03 entry to read "atomic conditional `updateMany` claims, `batchSize * 2` over-fetch, one round-trip per candidate"; add a comment at `poll()` naming the round-trip cost and the trigger for revisiting — a poll tick whose claim phase exceeds the poll interval, or a second worker instance. No new `$queryRaw` in this ticket.

- **12.2a Cross-module writes — `crm` exports an abstract class, and `marketing` never names a `crm` table again.** The six `cross-module-tables` violations are the real work in 12.2. `crm/index.ts` is deliberately empty today; it gains an abstract `CrmLeadIntake` declaring exactly what marketing needs — resolve-or-create a lead from inbound contact data, non-destructively fill empty fields, record a lead submission, append a timeline activity — with `LeadsService` bound to it in `CrmModule` and the module exported beside it. Reason: the map's headline decision was decoupled lead conversion; the events *are* emitted but the writes go straight at `Lead`, `LeadSubmission` and `Activity`, so the stated architecture and the code disagree, and ADR 0005 says boundaries are enforced mechanically rather than by discipline. **Rule:** the surface takes and returns marketing-agnostic DTOs — no `Prisma.*` types, no `companyApplied`, no `ScopedPrisma` in any signature; the ADR 0012 non-destructive fill moves *into* `crm` and becomes `crm`'s invariant instead of a rule marketing is trusted to honour; the `MARKETING_SYSTEM_USER_ID` actor is passed as a caller-identity parameter, never hardcoded inside `crm`. `crm-bridge.service.ts` keeps its name and its event emission and becomes a thin translator; `inbox.service.ts:462`'s `activity.create` goes through the same surface — no second path.

- **12.2b The transaction boundary crosses the module seam, so the surface must accept one.** Ticket 11 put the submission row, the counter and the lead write in one `prisma.$transaction`; routing the lead write through `crm` must not quietly break that. Reason: splitting them back into two transactions reintroduces exactly the orphaned-lead-in-the-pipeline bug 11.3c fixed, and it would be invisible in review. **Rule:** the `crm` intake methods take an optional transaction handle as their last parameter and use it when given; marketing passes its `$transaction` client. The `marketing.lead.captured` event still fires **after** commit, never inside. A test asserts that a forced failure after the lead write leaves no `Lead` row behind.

- **12.2c The remaining ten violations are mechanical — and `check:conformance` joins the definition of done.** `tracking.controller.ts` passes `@Query()` whole into `listQuery(query, SPEC)` per ADR 0004 instead of destructuring eight parameters; `social-accounts.service.ts:533` uses `listQuery(...).findMany()` so the page-size ceiling and identifier tiebreak apply; `ad-webhooks.controller.ts:28` declares a real validator, since there is no global pipe to fall back on and this is an unauthenticated third-party endpoint. Reason: these are one line each, but the `body-validated` one is a public surface accepting an unshaped body — the same class of defect as 11.3b. **Rule:** the ad-webhook validator checks the platform path parameter against a closed union and the body against a per-platform schema, rejecting unknown top-level keys with **400** and no stack detail; a payload that parses but carries no usable contact fields is a **202 no-op**, not a 400, so a platform's retry storm cannot be triggered by our own strictness. Separately, `npm run check:conformance` is added to the completion checklist and must be named explicitly in every remaining ticket's verification line — the process defect that let 16 violations accumulate from ticket 07 onward was the phrase quietly disappearing from the map.

- **12.3a Vault secret — fail closed at boot, in one place, for both secrets.** The `crypto.service.ts:29` fallback and the OAuth-state HMAC fallback at `social-accounts.service.ts:437` both disappear. Reason: deployed without the env vars, every token is encrypted under a key committed to this repo, which makes the service's own docstring ("cannot read tokens without the server's vault secret") false — and a secret that silently defaults is worse than no secret, because it looks fine. **Rule:** a single startup check — an `onModuleInit`, not a lazy check on first use — reads `MARKETING_VAULT_SECRET` and `MARKETING_OAUTH_STATE_SECRET`; when `NODE_ENV === 'production'` a missing or short (< 32 chars) value **throws and refuses to boot**; outside production a missing value derives a clearly-labelled ephemeral development key generated **per process** (`randomBytes`), never a constant, logged once as a warning. An ephemeral dev key means dev tokens do not survive a restart — that is intended, because it makes the production failure mode impossible to reach by accident. Drop `SESSION_SECRET` as a fallback source: reusing the session signing key as an encryption key couples two rotations that must stay independent.

- **12.3b Key rotation — `v1.iv.ct.tag` now, envelope encryption recorded as the direction.** Ciphertext gains a key-id prefix and the service holds a map of key ids to derived keys. Reason: today, rotating `MARKETING_VAULT_SECRET` bricks every stored token with no recovery but re-authorising every social account by hand — so in practice the key would never be rotated, and an unrotatable key is the real defect. **Rule:** `encrypt()` always writes `<kid>.<iv>.<ct>.<tag>`; `decrypt()` reads the kid and selects the key, and accepts a legacy three-part string as `v1` for exactly one release; the active kid comes from `MARKETING_VAULT_KEY_ID` (default `v1`), retired keys from `MARKETING_VAULT_RETIRED_KEYS` as decrypt-only `kid:secret` pairs. A decrypt naming an unknown kid returns a **distinct error code** from a tamper failure — conflating "we lost the key" with "someone modified this row" makes an operational incident look like an attack. Envelope encryption (per-record DEK wrapped by a KEK, so rotating the KEK re-wraps small keys and never touches bulk ciphertext) is the recorded end state; its trigger is a second secret store or a scheduled-rotation compliance requirement, not this ticket. **Test:** a token encrypted under `v1` still decrypts after `v2` becomes active.

- **12.3c IP hashing — the date is a rotation input, not the secret; add a pepper.** Reason: `tracking.service.ts:450` rotates the salt daily, which is the right instinct, but the salt *is* the date and therefore public — IPv4 is 2^32, so a DB dump plus a known salt de-anonymises every visitor in seconds, and the column is currently sold as a cookieless GDPR-safe hash. **Rule:** `hashIp` becomes `sha256(ip + ':' + yyyy-mm-dd + ':' + MARKETING_ANALYTICS_PEPPER)`, with the pepper covered by the same fail-closed boot check as 12.3a; it is never logged, never returned in any DTO, and deliberately **not** rotated on a schedule, because rotating it breaks visitor-uniqueness continuity across the boundary — that trade is written down next to the constant. Keep the 16-hex truncation. No raw IP is persisted anywhere, including inside `rawPayload` blobs on webhook or submission rows.

- **12.3d Retention — one scheduled job on the queue this module already owns, with the window as data.** Add a recurring `marketing.retention.purge` job deleting `PageViewEvent` rows past the window in bounded batches. Reason: `grep deleteMany|retention|purge` returns nothing across the module, so `PageViewEvent` grows unbounded — a cost problem and a GDPR storage-limitation problem on the one table holding pseudonymous visitor data. **Rule:** default window **180 days**, from `MARKETING_ANALYTICS_RETENTION_DAYS`; the purge runs under `withoutCompanyScope` with an explicit reason string and deletes in capped batches (10k), re-enqueuing itself while a batch comes back full, so one tick can never hold a long table lock; it purges raw event rows only — aggregates already computed stay. The job self-schedules its next run rather than relying on a cron the deploy does not have, and is registered at module init only when one is not already pending, so a restart cannot fan out duplicates. Zero new infrastructure, consistent with the module's charter.

- **12.3e `SmartLink.clicks` becomes rows, and the JSON column is left behind rather than migrated in place.** Reason: it is a read-modify-write on a JSON column driven by a public endpoint, so concurrent clicks silently lose updates — and losing click data on an attribution feature makes the whole feature untrustworthy, not merely slightly wrong. **Rule:** a new `SmartLinkClick` table, one row per click, **insert-only** — no upsert, no counter increment, nothing to contend on; reads aggregate with `count`/`groupBy`; the pruned-to-500 JSON array is kept read-only for one release so existing bio pages keep rendering history, and is dropped in a follow-up migration once the rows table covers the window. Clicks are written outside any user-facing transaction — a failed click insert must never fail the redirect or the page. Test: N concurrent clicks on one link produce exactly N rows.

- **12.3f Origin isolation stays deferred, and ticket 11's finding narrows the trigger.** Ticket 11 verified this application has no session cookie at all — the session is a JWT in `localStorage` sent as `Authorization: Bearer` — so the 11.2d cookie-scoping rule has no subject and the `/b/:slug` origin split buys less than 11.2d assumed. Reason: with no ambient credential, a renderer mistake on the bio page cannot ride a cookie into an authenticated request; the residual risk is `localStorage` token theft by same-origin script, which the ticket-11 CSP already blocks at the `script-src 'nonce-…'` line. **Rule:** the split remains deferred with its trigger unchanged (a customer-facing custom domain, or the first bio-page feature embedding third-party content) and is explicitly **not** in ticket 12's scope; the `localStorage` trade-off is recorded here rather than re-derived next time. Do not spend ticket 12 on infra.

Every outbound fetch runs inside a queue worker, never inside a request handler, so a slow host cannot occupy an HTTP thread.

- **14a AI assistant — the API key is a platform secret, not a tenant secret, and it never leaves the server.** Add `ANTHROPIC_API_KEY` as a fourth entry in `MARKETING_SECRET_VARS` (`vault-secrets.ts`) so it inherits the ticket-12 rule: absent in production refuses the boot, absent in development gets an ephemeral value and a warning, and there is no hardcoded fallback to copy. Reason: the vault (`CryptoService`) exists to hold *per-tenant* OAuth tokens; putting one shared vendor key through per-record encryption buys nothing and couples two rotation schedules that have to stay independent (12.3b). **Rule:** generation happens only behind an authenticated `POST /api/marketing/ai/compose` on the server; the key is never sent to the browser, never surfaced in a masked-credential list, and never logged — and the endpoint carries a `@Throttle` from ticket 11's `ThrottlerModule` plus a per-company daily token budget counted in rows and checked *before* the call, not after.

- **14b Brand context is a closed field allowlist; CRM personal data never reaches the model.** The composer sends the draft the user typed plus a `brandId`; the server assembles the prompt from an explicit list — brand name, tone/voice string, product description, target platform, character limit — and nothing else. Reason: the open question the classifier caught ("does brand context include lead names, email address, phone number?") has one safe answer, and answering it in code later means answering it by accident. **Rule:** the prompt builder takes typed fields, not a `Record<string, unknown>`; a request carrying free-form `context` beyond the allowlist is rejected by the schema rather than trimmed; the AI path issues **no query against `crm` tables at all** — which also keeps it on the right side of the `cross-module-tables` conformance rule that produced six of ticket 12's violations.

- **14c Text from outside the tenant is data, never instruction, and model output can only fill a field a human accepts.** Inbox messages (ticket 08), competitor metadata (15) and RSS entries (16) are all attacker-controllable text that will plausibly be fed to the model. **Rule:** untrusted text is passed inside a clearly delimited data block with a standing system instruction that content within it is data to summarise, never instructions to follow; and — the load-bearing half — **no model output takes an action**. It populates an editable draft field the user must explicitly accept. Nothing generated auto-schedules, auto-publishes, or auto-sends an inbox reply, so the worst case of a successful injection is a bad suggestion the user reads, not a post on a client's Instagram. Alt-text and hashtag generation are subject to the same rule.

- **14a-bis Key resolution goes through one function from day one.** Every model call resolves its credential and endpoint via `resolveAiProvider(companyId)`, never by reading `process.env` at the call site. Reason: the platform-vs-tenant question and the which-vendor question are both commercial decisions that can change after this ships, and a single resolver makes either one a second branch inside one function rather than an edit to every call path. Today it returns the platform secret and ignores its argument — the argument is there so the signature does not have to change later.

- **14d The allowance is the product decision; the model price is a footnote.** Research into how the category actually pays for this (7 Sep 2026, three agents, sources in `hardening-and-design-research.md`) found the answer is metering, not cheap models: **Later ships 5 caption credits per month on a $18.75/mo plan; Metricool ships 5 per brand per month and counts alt-text against them.** Nobody below $79/seat ships uncapped. **Rule:** the assistant ships with a Later-sized allowance of **20 generations per tenant per month**, resets monthly, no rollover — enforced server-side as a hard ceiling, not a forecast. At ~20 tenant companies that is roughly 400 calls a month, about **$1/month on Haiku 4.5**, which is what makes the platform key (14a) affordable in the first place. The cap is denominated in **dollars** computed from `response.usage`, not in request counts, so a model or prompt change cannot quietly raise the ceiling. Sizing the allowance is a pricing decision the owner makes, but it is set *before* the feature ships, never retrofitted after a bill arrives.

- **14e Token hygiene, and two levers that were assumed to exist and do not.** Output is ~77% of this workload's cost at every provider surveyed, so the cheap wins are on the output side. **Rule:** one call returns N variants — never N calls for N variants, which pays the brand-voice prefix N times; and `max_tokens` is capped per generation type from the real shape of the output (a caption is 30-60 tokens, so ~250 for a three-variant response, not a 400+ default). Two things this design must **not** rely on, both verified rather than assumed: **prompt caching is a non-lever here** — the minimum cacheable prefix is 1,024 tokens on Anthropic and OpenAI and 2,048-4,096 on Gemini, and this prompt is ~600, so it never fires on any of them; and **the Batch API's 50% discount does not apply** — the composer is an interactive regenerate loop with a human waiting, and batch endpoints are hours-latency. Batch remains correct for any bulk path (a whole autolist, a media-library alt-text sweep), which is the one place it should be mandatory.

- **14f Zero-inference features ship first, and are not called AI.** Most of what a composer's users experience as intelligence needs no model. **Rule:** build, in this order, before any generation feature — per-platform character/format/media-limit validation; **best-time-to-post computed from this tenant's own tracking-pixel and engagement data** (ranked highest-value by the research: Metricool's 2026 survey of 700+ professionals found analytics use rose 32% → 59% year over year, and what they ask for is exactly this); readability, spam-word and emoji-density linting; hook-formula and caption templates; a first-comment and CTA snippet library. Each is days of work, costs nothing per call forever, and cannot hallucinate a brand's voice. Two exclusions with reasons: **hashtag suggestion is cut** — Instagram removed hashtag-following in December 2024 and Meta has said publicly that hashtags do not drive reach, so it is a 2026 build of a 2019 feature; and **alt-text is the one item to absorb as a real inference call**, because deriving it from EXIF or filenames produces garbage users notice immediately, and it carries a legal driver rather than a taste one — the European Accessibility Act has applied since 28 June 2025 and reaches social content.

- **14g Provider is a seam, with two disqualifications recorded now rather than rediscovered later.** Haiku 4.5 stays the default: at the 14d allowance it costs about a dollar a month, and swapping vendors to save that dollar buys an unverified data-retention chain for twenty tenants' business data. **Rule:** if the owner does elect to switch, it happens behind 14a-bis and only to a provider with a written retention position — **Mistral Ministral 3 8B** ($0.15/$0.15, EU-domiciled, first-party, ~$1.08/mo at 7,200 calls) and **Groq gpt-oss-20b** (self-serve zero-data-retention toggle) are the two that cleared; providers whose retention policy could not be found at all (DeepInfra, Novita, Together, Fireworks) are excluded regardless of price. Two hard bars: **Google's Gemini free tier is disqualified twice over** — its terms let Google train on prompts and responses with human review, and separately permit only *paid* services when the API client is made available to users in the EEA, Switzerland or the UK, which a multi-tenant ERP cannot satisfy; and **self-hosting is closed, not deferred** — break-even against Haiku is ~207,700 calls/month on the cheapest GPU that meets the 1-3 second latency budget, roughly 29× the realistic volume, while scale-to-zero serverless is disqualified before cost on 15-30 second cold starts against traffic arriving once every two minutes. Revisit only if monthly spend passes ~$500; that is a trigger, not a project. **Nothing in this table is benchmarked on short-form marketing copy — no such public evaluation exists** — so any switch is gated on a blind A/B of ~200 real drafts, which costs under a dollar to run and is the only evidence that will exist.

- **14h BYO key is the escape valve, not the cost strategy.** A tenant who needs 500 generations a month gets to bring their own key rather than an angry churn conversation. Reason: **Publer does exactly this at a $10/account price point** — on its Free and Professional tiers the AI assistant works only with the customer's own key, billed to them directly — so it is proven commercially in this category at these economics. **Rule:** the tenant key is a per-tenant secret and therefore goes in the existing encrypted vault (`CryptoService`, `v1.iv.ct.tag` format, masked from the decrypted value per 11.4a), resolved through 14a-bis, and it *raises* that tenant's allowance rather than replacing the metering. Expect low single-digit adoption; do not model it as a revenue lever or as a substitute for 14d's cap.

- **15a Competitor benchmarking uses official APIs only; the scraper option is closed, not deferred.** The map framed this as "public profile scraping **vs.** official graph APIs" — settle it as APIs. Reason: scraping adds an operator-supplied-URL fetch path (14-17.0), breaks on every markup change, and sits against the platforms' terms while providing nothing the connected account's own endpoints do not. **Rule:** competitor metrics are read through `ISocialNetworkAdapter`, which gains a `fetchPublicProfileMetrics(handle)` implemented per network; there is no HTML-parsing fallback anywhere in the module. A network whose API exposes no public profile metrics stores the competitor row and renders "not supported on this network" — an honest empty state, which this module already does well, rather than a scraper smuggled in behind a feature flag.

- **15b Competitor reads borrow a connected account's token, so they are authorized and metered like publishing.** **Rule:** the snapshot job loads the `SocialAccount` by `(companyId, brandId, network)` — never by id alone — decrypts through `CryptoService`, and refuses if the brand has no connected account for that network rather than falling back to an app-level token. Those reads consume the same quota ledger as publishing (`publishing-quota.ts`), because Meta and X count them against the same limit; a benchmarking poll that silently eats a brand's 50/24h publish budget is ticket 11's rate-limit bug in a new place. Snapshots are append-only rows with a capture date, so nothing is read-modify-written on a JSON column (12.3e).

- **15c Store aggregates, not content.** **Rule:** a snapshot row holds follower count, post count, engagement rate and the capture date for a public business handle — no post bodies, no commenter names, no profile photos mirrored into our storage. Reason: competitor post content is third-party copyright and its commenters are people who never dealt with us, so collecting it turns a metrics feature into a personal-data processor. Snapshots expire through the existing `RetentionService` job (`RETENTION_JOB_TYPE`) with their own configurable window, rather than a second scheduler.

- **16a Feed URLs are validated twice — at write time for shape, at fetch time for destination.** **Rule:** the feed URL goes through `readLinkUrl` from `schemas.ts`, narrowed to `https:`, when saved, and through `OutboundFetchService` (14-17.0) on every single poll. Neither check substitutes for the other: the first gives the operator an immediate error message, the second is the one that actually holds, because the DNS answer is what changes between them.

- **16b Ingest is idempotent by key, and it produces drafts, not published posts.** **Rule:** a unique index on `(brandId, feedId, entryKey)`, where `entryKey` is the feed's `<guid>` when present and `sha256(link + '\n' + title)` when it is not; ingest is create-if-absent against that key, so a re-poll, a retry after the 12.1b fence rejects a stale worker, or a feed that renumbers its items can never produce a second `ScheduledPost` for the same entry. Reason: "auto-enqueue into scheduling queues" plus at-least-once delivery is a double-publish generator, and this module has shipped that bug once already (11.4b). Ingested items land as `DRAFT` for a human to schedule; auto-publishing straight from a feed is out of scope for this ticket, not a config flag.

- **16c One poll job per feed, on the queue that already exists.** **Rule:** follow `RetentionService`'s enqueue pattern exactly — before scheduling, check for a live `PENDING`/`PROCESSING` job of that type for that feed and skip if one exists, so N deploys do not create N pollers. The lease reaper and the `attempts` fence from 12.1a/12.1b are what make a worker that dies mid-ingest safe; do not add a second scheduling mechanism, a cron, or a `setInterval` beside the queue.

- **16d Feed content is untrusted text on a rendering path.** **Rule:** entry titles and descriptions are stored and rendered as **text**, never as HTML — no feed markup reaches a `dangerouslySetInnerHTML` or the server-rendered bio page; every link and enclosure URL from a feed passes `readLinkUrl` before it is stored, and an entry whose link fails is dropped rather than stored with a broken href. If an entry is later handed to the composer's assistant it is untrusted data under 14c.

- **17a Editor integration is a popup OAuth redirect with a fixed `redirect_uri`, not a vendor iframe holding our session.** This settles the open question the classifier caught. Reason: an iframe of a third-party editor inside an authenticated ERP page puts vendor script one framing bug away from our session, and this app keeps its JWT in `localStorage` (12.3f) where a same-origin script can simply read it. **Rule:** `redirect_uri` is a server-side constant per vendor, never read from the query string; the callback verifies the HMAC-signed `state` exactly as `social-accounts.service.ts` does today, under `MARKETING_OAUTH_STATE_SECRET`, and rejects on mismatch, expiry, or reuse; after the callback the server redirects only to a path on **our** origin drawn from a closed allowlist — no `returnTo`, `next`, or `continue` parameter is honoured, which is the whole class of open redirect the classifier flagged.

- **17b Vendor refresh tokens live in the same vault, under the same masking rule.** **Rule:** store through `CryptoService` in the `v1.iv.ct.tag` key-id format (12.3b), on a row scoped by `companyId` + `brandId` + connecting `userId`; the API returns a masked handle derived from the **decrypted** value, never a slice of the ciphertext — that was ticket 11's `maskToken` bug (11.4a), and a second implementation of a vault is exactly where it comes back. Tokens are never returned to the client in any form, and disconnecting revokes upstream *and* deletes the row rather than flagging it inactive.

- **17c `postMessage` is validated on origin and shape, and the returned asset goes through the fetch guard.** **Rule:** the handler compares `event.origin` against an exact vendor-origin allowlist (string equality, not `endsWith` — `evilcanva.com` ends with `canva.com`), validates the payload shape before touching it, and ignores everything else silently; outbound messages name the vendor origin explicitly and never `'*'`. The asset URL the vendor hands back is a user-influenced URL like any other: `readLinkUrl` first, then `OutboundFetchService` to download it, with the 2 MB and timeout caps applied.

- **17d Connecting an editor is a brand-level permission, not a per-user convenience.** **Rule:** only a `BrandMember` with the publishing role may connect or disconnect an editor account, checked server-side on both routes; the connection is scoped to the brand, so a member removed from a brand loses the editor along with the social accounts. Reason: an editor account can pull assets into any brand's composer, which is the same mis-posting hazard 13.2d is built around.

- **14-17.e Two tickets, phased, with the gate.** The four "Not yet specified" items consolidate into **two** tickets rather than five: **14 Composer intelligence** (14a-14h) and **15 External content sources** (14-17.0, 15a-15c, 16a-16d, 17a-17d). Reason: the owner asked for the full scope in fewer tickets, and the honest seam is the composer versus everything that reaches outside it — the outward three already share `OutboundFetchService`, so splitting them was bookkeeping, not decoupling. Decision IDs are deliberately **not** renumbered; ticket 15 carries the `16x` and `17x` IDs and says so. **Rule:** fewer files must not mean coarser delivery — **phases inside each ticket ship independently**. Ticket 14 Phase 1 (the model-free work) has no blockers and must not wait on Phase 2, which is gated on the owner's allowance figure and the 14g A/B; ticket 15.1 (`OutboundFetchService`) goes first because 15.2-15.4 consume it, and 15.4 is blocked on two vendor OAuth registrations that are not engineering work. Neither ticket opens until `npm run check:conformance`, `npm run test:backend` and `npm run test:app` are quoted green in ticket 13's resolution — the audit named "adding a feature area to a module whose checks are red" as the defect that produced this entire hardening pass.

### Ticket 14 — design pass (2026-09-07, decisions only; no code written)

`./scripts/classify-ticket.sh .scratch/marketing-automation/issues/14-composer-intelligence.md`
returns **3 strong, 1 weak → OPUS**: credentials & secrets (real, Phase 2), PII / personal data
(real, and wider than the classifier's line — see 14l and 14r), cross-tenant authz (weak, real,
and Phase 1 — see 14i), and *public / unauthenticated surface*, which is a **false positive**: it
matched the sentence disqualifying Gemini's free tier. Nothing in ticket 14 is unauthenticated;
every route either phase adds sits behind the module's normal auth. Decisions 14a-14h stand as
written; the entries below are the gaps that pass left, and they are rules, not suggestions.
Where a rule conflicts with an existing test, the code is wrong, not the test.

- **14i Phase 1's analytics read is a tenancy decision, not a reporting one.** Best-time-to-post reads posting history across a brand, which is the module's first aggregate query whose result is *advice* rather than a list, so it will not inherit the `ListSpec` scoping the rest of the module gets for free. **Rule:** every query behind the recommendation filters on `companyId` **and** `brandId`, with `companyId` taken from the authenticated context and never from the request body, and the caller's `BrandMember` row is verified before the query runs — the same shape `brands.service.ts` uses today. `brandId` alone is never a sufficient key; a brand id is a uuid an ex-member still has.

- **14j The recommendation's provenance is a required field, not a UI string.** The ticket's "say which one is being shown" only holds if the API cannot express a recommendation without saying where it came from. **Rule:** the response carries `source: 'tenant' | 'cohort' | 'global'` and `sampleSize` as **non-optional** fields and the UI label is derived from them rather than decided client-side; `source: 'tenant'` requires at least 30 posts with metrics for that `(brandId, network)` in the trailing 90 days, below which it degrades to `cohort` and then `global`. The computation runs as a `MarketingJob` on the existing queue following `RetentionService`'s enqueue pattern (skip if a `PENDING`/`PROCESSING` job of that type already exists for that brand), never inside the request handler — a 90-day aggregate is not something to compute while a composer waits.

- **14k Hours are bucketed in the brand's timezone.** `MarketingBrand.timezone` already exists and defaults to `'UTC'`. **Rule:** timestamps are stored and queried in UTC and bucketed into hour-of-week using the brand's timezone, never the viewer's browser timezone. Reason: two users in different offices must see the same advice for the same brand, and a recommendation that moves when you travel is one nobody trusts twice.

- **14l The best-time aggregate never touches visitor-level rows.** `PageViewEvent` carries `visitorId`, `ipHash`, `country` and `device`; a posting-time recommendation needs none of them. **Rule:** the aggregation projects a time bucket and a count and nothing else — no `visitorId`, `ipHash` or `sessionId` reaches the projection, the response, a log line or a cached artifact — and any bucket with fewer than 5 underlying events is merged into its neighbour rather than displayed, so a low-traffic brand's heatmap cannot become one visitor's browsing schedule. This is what the classifier's PII signal actually means in Phase 1.

- **14m Limit validation is server-authoritative; the composer's copy is UX.** A validator that runs only in the browser is a warning, not a limit, and the failure it prevents happens on the server. **Rule:** the per-network table is a single frozen constant in the shared package that both `application/` and `backend/` import — never two tables — and `social-publisher.service.ts` re-runs it against the resolved account's network immediately before handing content to the adapter, refusing with the same message the composer showed. The client check may be skipped; the publish check may not.

- **14n Linting warns and never blocks.** Readability, spam-word, emoji-density and caps checks are heuristics with real false positives, and a heuristic that can refuse a publish becomes a support ticket the day a client's brand voice is legitimately shouty. **Rule:** lint results carry severity `warning` only, the publish path does not read them at all, and the linter is a pure function over the draft — no network call, no model, no persisted result per keystroke.

- **14o Templates and snippets are literal substitution, not a template engine.** Hook skeletons invite a templating library, and a templating library evaluated over tenant-supplied text is an injection surface bought for no benefit. **Rule:** placeholders come from a fixed, closed key set (`{subject}`, `{brand}`, `{cta}`) replaced by literal string substitution; no Handlebars, no `eval`, no `new Function`, no dynamic property access driven by the template string. Snippet bodies are stored and rendered as **text** — inserted as a `textarea` value, never reaching `dangerouslySetInnerHTML` — and the snippet table is scoped by `companyId` + `brandId` like every other row in this module.

- **14p The allowance is a ledger decremented before the call, atomically.** 14d says "hard server-side ceiling"; two concurrent regenerate clicks reading the same balance are exactly how a ceiling degrades into a forecast, and this module has already shipped one at-least-once double-spend (11.4b). **Rule:** spend is an **append-only** ledger row plus a conditional update — `UPDATE ... SET spent_cents = spent_cents + :estimate WHERE company_id = :c AND period = :p AND spent_cents + :estimate <= cap_cents`, where **zero rows affected means refuse** — committed *before* the provider call; after the response a second append row reconciles the estimate to the real cost from `response.usage`. A call that fails, times out or is aborted reconciles to zero cost, so a provider outage cannot eat a tenant's month. The period key is `YYYY-MM` in UTC with no rollover, and the counter is a column, never a field inside a JSON blob (12.3e).

- **14q The client chooses nothing that costs money.** Showing remaining allowance before generating (14d) needs its own read, and every knob exposed to the client is a knob that raises the bill. **Rule:** `GET /api/marketing/ai/allowance` is authenticated and company-scoped and returns cap, spent and reset date; the compose request schema accepts the draft, `brandId`, target platform and variant count only — a body carrying `model`, `maxTokens`, `temperature`, `apiKey` or a cost figure is **rejected by the schema**, not trimmed, because the server picks all of them. The refusal when the ledger is exhausted names the reset date and is returned before any provider call is attempted.

- **14r Prompts and completions are never logged.** The draft is the tenant's unpublished business content and — once the composer is fed an inbox message under 14c — potentially a customer's own words; a debug log is the easiest way for that to leave the tenant boundary permanently. **Rule:** the generation audit row and every log line record `companyId`, `brandId`, `userId`, model, input/output token counts, latency and outcome, and **no prompt text, no completion text, no untrusted data block**. Provider errors are logged with the vendor's message and status only, request body stripped, and no APM or telemetry sink is handed the payload. The `ANTHROPIC_API_KEY` appears in no log, no error message, no masked-credential list and no response body (14a).

- **14s Model output is text on a rendering path.** Output arrives from outside the tenant just as inbox text does, and 14c constrains only what it can *do*, not how it is displayed. **Rule:** a completion is normalised (control characters stripped, trimmed to the target network's cap from 14m) and placed in an editable `textarea` value; it is never rendered as HTML or as markdown with HTML enabled, and never written to a bio page or any server-rendered surface without the escaping a user-typed field gets.

- **14t Alt-text is blocked on ticket 15.1, and the image URL never comes from the request.** A vision call needs image bytes, the images live at URLs in `ScheduledPost.mediaUrls`, and grepping the module confirms it still has no SSRF guard — so alt-text is the one Phase 2 item with a hard cross-ticket dependency. **Rule:** alt-text does not ship before `OutboundFetchService` (14-17.0) exists, and every image is fetched through it under its https-only, private-range, redirect-revalidation, 10s and 2 MB rules. The URL is looked up from a `ScheduledPost` (or media row) already scoped to `(companyId, brandId)` — the client sends a post id and an index, never a URL — so the vision path cannot be turned into a fetch primitive by anyone holding a composer login.

- **14u The interactive endpoint refuses bulk, structurally.** 14e's batch rule holds only if the cheap path cannot be reached in a loop from the browser. **Rule:** `POST /api/marketing/ai/compose` accepts exactly one draft and at most one image, returns N variants in **one** response (14e), and rejects an array of items with a 400 naming the bulk route; bulk alt-text and autolist sweeps are `MarketingJob` rows calling the provider's batch endpoint and drawing on the same 14p ledger. The `@Throttle` on the interactive route (14a) is a second fence behind the ledger, not a substitute for it.

- **14v BYO key: brand-publisher only, verified at save, and it never falls back.** 14h settles storage and metering but not who may set a key or what happens when it stops working. **Rule:** only a `BrandMember` with the publishing role may set, rotate or delete a tenant key, checked server-side on every route (the 17d rule); it is stored through `CryptoService` in `v1.iv.ct.tag` and masked from the **decrypted** value (11.4a), never returned in any form; it is validated at save time with one minimal probe call so a typo fails in settings rather than mid-composition; and when the tenant key is rejected at generate time the request **refuses** with "your API key was rejected" — never a silent fall back to the platform key, which would spend the shared budget invisibly and hide a broken credential for a month. Deleting the key returns that tenant to the 14d platform allowance.

- **14-17.0a The guard validates an address and then connects to that address.** 14-17.0 says "resolve the hostname and refuse private ranges" and "re-check at fetch time", but a resolve-then-fetch-by-name sequence re-resolves inside the HTTP client, and a DNS rebind that answers publicly on the first query and `127.0.0.1` on the second walks straight through a check that passed. **Rule:** `OutboundFetchService` resolves the host itself, filters the answer set, picks one surviving address and **connects to that literal IP** with the original hostname carried in the `Host` header and in TLS SNI, so the validated address and the connected address are the same value; if the resolver returns no public address the fetch is refused. Port is part of the check — **443 only** — because an internal service on `:9200` behind a public DNS name defeats a range check that only looks at the address.

- **14-17.0b Redirects are followed by us, one hop at a time, never by the HTTP client.** "Re-run the check after every redirect" is unimplementable if the client follows redirects internally: by the time control returns, the private-address hop has already been requested. **Rule:** every call sets `redirect: 'manual'`; each `Location` is resolved against the current URL and then re-enters the **full** 14-17.0 validation from the top (https, port, resolve, range, pin) before the next request is issued; a non-`https:` or unparseable `Location` ends the chain with a refusal; at most 3 hops; and request headers are rebuilt per hop rather than carried, so nothing accumulates across a cross-host jump.

- **14-17.0c Caps are enforced on bytes read, not on what the server claims.** A 2 MB cap checked against `Content-Length` is a cap an attacker sets to `0`, and a gzip stream expanding 1000:1 is 2 MB on the wire and gigabytes in the worker's heap. **Rule:** the body is consumed as a stream with a running byte counter that aborts the socket at 2 MB **after decompression**, the 10s budget is a wall-clock deadline over the whole chain (connect + all hops + body) enforced by an `AbortController`, and both refusals are ordinary outcomes the caller handles, not exceptions that kill the worker.

- **14-17.0d A refused or failed fetch reports a reason code, never the remote response.** Blind SSRF becomes useful SSRF the moment the operator can read what came back; a "feed error" panel that echoes status lines, headers or body snippets from `169.254.169.254` is an exfiltration channel with a UI. **Rule:** the guard returns a closed enum — `blocked_scheme`, `blocked_address`, `too_many_redirects`, `too_large`, `timeout`, `http_error` (status class only), `parse_error` — and the operator-facing surface and the logs render **only that code plus the URL the operator typed**. No response header, body fragment or resolved IP is stored on the feed row or returned by any API.

- **14-17.0e Outbound concurrency is bounded per host and per brand.** Every consumer of the guard runs on the queue, and a queue with no fan-out limit turns a list of operator-supplied URLs into a small DoS engine pointed at a third party — and, when a host is slow, into a worker-pool exhaustion of our own. **Rule:** at most one in-flight request per remote host and a fixed global ceiling across the module's fetch workers; a brand is capped at a fixed number of configured feeds and competitor rows (a plain count check at create time, refusing with a message, not silently); and a host that fails is subject to 16f's backoff rather than being retried at poll cadence.

- **16e The feed parser runs with entities and DTDs disabled.** Feed ingest is XML parsing of an attacker-chosen document, and the default posture of most XML parsers — resolve DTDs, expand entities — is `SYSTEM "file:///etc/passwd"` and the billion-laughs expansion, both of which land inside the worker with no network guard involved. **Rule:** the parser is configured DTD-off, external-entity-off, entity-expansion-off, with a node-count/depth ceiling; the 2 MB body cap from 14-17.0c is applied **before** parsing, not after; a document that fails to parse yields `parse_error` (14-17.0d) and leaves the feed's last-success state untouched. JSON Feed, if supported, is parsed with the platform JSON parser and no reviver.

- **16f A feed that keeps failing is backed off and then disabled, visibly.** 16c guarantees one poller per feed but says nothing about a feed that 500s or times out forever, and a fixed-cadence poller against a dead host is both a wasted worker slot and an unpaid-for hammer on someone else's server. **Rule:** consecutive failures raise the next poll delay geometrically to a ceiling; after a fixed consecutive-failure count the feed is set `DISABLED` with its last reason code, stops being scheduled, and shows the operator a re-enable action; a single success resets the counter. Disable is a state on the feed row, never a deletion of the operator's configuration.

- **16g `entryKey` is always a hash, so the index is bounded and the identity is stable.** 16b's key is "the `<guid>` when present" — a value an arbitrary publisher controls, unbounded in length, and free to differ by a trailing space or a Unicode form between polls, which is a duplicate draft or a failed index write depending on which. **Rule:** `entryKey` is always `sha256` hex of a canonical string — `'g\n' + NFC(trim(guid))` when a guid exists, `'l\n' + NFC(trim(link)) + '\n' + NFC(trim(title))` otherwise — so the column is a fixed 64 chars, the prefix keeps the two derivations from colliding, and the unique index on `(brandId, feedId, entryKey)` is the whole dedupe mechanism, with ingest writing create-if-absent and treating the constraint violation as success.

- **16h A draft carries its provenance, and an excerpt rather than a reproduction.** A feed entry is someone else's copyrighted text arriving on a path that ends at a publish button, and a draft that looks like original copy invites republishing it whole under the brand's name. **Rule:** the draft records `feedId`, `entryKey`, the canonical entry link and the fetch timestamp as columns, the stored description is **truncated to a short excerpt** rather than kept in full, and the composer renders the source link beside it. Enclosures are stored as validated URLs only — no media is downloaded at ingest; an operator action pulls one through `OutboundFetchService` later, which keeps a feed from spending our bandwidth unattended.

- **15d A competitor handle is an identifier, not a URL, and it never reaches the fetch guard.** 15a closes scraping, but the field an operator types is still free text, and "handle" fields that quietly accept `https://…` are how a closed scraper path reopens as a "convenience". **Rule:** the handle is validated per network against a conservative charset and length (letters, digits, `_`, `.`, `-`; no scheme, no `/`, no whitespace) and **rejected**, not sanitized, when it fails; it is passed to `ISocialNetworkAdapter.fetchPublicProfileMetrics(handle)` as a parameter to the adapter's own fixed endpoint; no competitor code path constructs a URL or calls `OutboundFetchService` at all.

- **15e Competitor reads reserve quota before the call and never starve publishing.** 15b puts benchmarking on the publishing ledger, which is right, but a background poll reading a balance and then spending it has the same two-concurrent-readers hole 14p was written to close — and unlike a composer click, this one can silently consume the budget a scheduled post needs at 9am. **Rule:** the snapshot job reserves against the ledger with the same conditional update as 14p (zero rows affected means refuse), **before** the adapter call, reconciling to zero on failure; and competitor reads refuse below a reserved floor of the brand's window that only publishing may draw on, so an exhausted benchmark budget degrades to "snapshot skipped, quota reserved for publishing" rather than a failed post.

- **15f One snapshot per competitor per day, enforced by the index.** Snapshots are append-only (15c) and the poller is at-least-once, which without a key means a retry writes a second row for the same day and every engagement-rate chart quietly double-counts. **Rule:** a unique index on `(brandId, competitorId, network, captureDate)` with `captureDate` a UTC date, ingest create-if-absent against it; the poll job is deduped by the 16c pattern; and a vendor `429` backs the competitor's next window off through the publishing adapter's existing limiter rather than being retried immediately, because the token being throttled belongs to the brand's real account.

- **17e `state` is single-use because a row says so, not because a signature says so.** 17a requires rejecting replay, and an HMAC-signed self-contained `state` cannot detect its own second use — the signature verifies identically every time. **Rule:** the callback is guarded by a persisted nonce row created at authorize time carrying `companyId`, `brandId`, `userId`, vendor and expiry; the callback consumes it with a conditional delete/update whose zero-rows result is a refusal; the flow additionally uses **PKCE** (`S256`) with the verifier held server-side; and the identities the callback writes come from that row, never from the callback's own query string.

- **17f The popup returns a signal, never a credential.** The code-for-token exchange is server-side, but the popup still has to tell the opener it finished, and the easy version of that message is the one carrying the code or the token through the browser. **Rule:** the callback page `postMessage`s a fixed literal `{ source: 'marketing-editor', vendor, ok }` to **our own origin by exact string**, and nothing else — no code, no token, no vendor payload; the opener re-reads connection state from our API after receiving it; and the callback page is served with a restrictive CSP and `X-Frame-Options: DENY` so it cannot be framed by the vendor page that opened it.

- **17g A returned asset is content-sniffed, size-capped and re-hosted.** 17c sends the asset URL through `readLinkUrl` and the fetch guard, which settles *where* we may connect but not *what* we accept; an editor export is attacker-influenceable, and an `image/svg+xml` served back on a brand's own domain is a stored-XSS payload with a picture frame around it. **Rule:** a fixed content-type allowlist (`image/png`, `image/jpeg`, `image/webp`, `image/gif`, `video/mp4`), verified by **magic bytes** and not by the vendor's `Content-Type` header, with `image/svg+xml` refused outright; a size cap at the 14-17.0c limit; the bytes are stored in our own media location under a generated name with any vendor-supplied filename discarded, and the composer references **our** URL — the vendor URL is never persisted as a `mediaUrl`, because a hotlink is a fetch we cannot re-validate at publish time.

- **17h Vendor secrets are env-only, scopes are minimal, and disconnect follows brand membership.** 17b and 17d settle token storage and who may connect; the surrounding facts — where the vendor *client* secret lives, and what happens when a member leaves — are where a second vault implementation usually diverges from the first. **Rule:** vendor client ids and client secrets are read from `process.env` at startup through the same config path as `MARKETING_OAUTH_STATE_SECRET`, never stored in the database, never returned by any endpoint and never included in a masked-credential listing; the authorize URL requests the narrowest documented scope for exporting a design and no publishing scope; and removing a `BrandMember` runs the same revoke-upstream-and-delete-row path as an explicit disconnect for that user's editor rows on that brand, so 17d's boundary holds after the fact and not only at connect time.
