# 06 — Products and units of measure (Core), and the module generator

**What to build:** The product master as its own Core module beneath inventory — and the generator
that produces every module after it.

I can define units of measure and the products I deal in, with a cost, and edit or deactivate them.
Nothing is seeded, including units of measure — I create the ones my business uses. Products sits
beneath inventory so that Sales, Purchase, Manufacturing and E-commerce depend on Products rather
than on the whole inventory module.

The generator is extracted here, from three modules that already exist, and Products is the first
module produced by it. That ordering matters: a generator written before any module exists encodes
guesses, while one extracted from working modules encodes what actually turned out to be needed.
With forty-plus modules ahead, consistency cannot come from discipline — it comes from the starting
point being correct.

## Comments

**2026-08-03 — built. The generator, and what it turned out to be.**

*It was extracted, not designed.* Identity, hrm and parties were written by hand first, and
the templates are what those three turned out to need. That ordering is the whole argument
of this ticket and it paid off in a way worth recording: the first thing generating products
found was that a module's public surface has to export its Nest module as well as its
contract, because a consumer cannot inject `PartyDirectory` without importing
`PartiesModule`. A generator written at ticket 02 would have got that wrong and thirty-nine
modules would have inherited it. ADR 0006 records the rest.

*What it produces is a working module rather than a skeleton.* A table, a list endpoint under
the platform's conventions, a create form, a screen with its empty state, HTTP tests and
screen tests. That is deliberate: a skeleton with `TODO` in it leaves exactly the decisions
that need to be consistent — paging, scoping, error shape — to whoever is writing the
eleventh module at four in the afternoon.

*It also makes the three edits a directory cannot express*: the model in `schema.prisma`, the
classification in `company-owned.ts`, and the contract's line in `packages/src/index.ts`.
Anchored patches, applied in memory first — so a moved anchor costs nothing and half a
generated module never reaches disk.

*The plan is a pure function*, as the conformance pack is, and for the same reason: the test
hands what the generator *would write* to `assembleModules` and `checkConformance` — the same
two functions the build runs — instead of writing eleven files into the working tree and
hoping to clean up after a failure.

**The one criterion that is weaker than it reads.**

"A test proves a freshly generated module builds, boots and passes the pack." Passes the pack
and assembles are proved by `test/generator.spec.ts` against the real rules. **Builds and
boots are proved by products**, which was generated by the generator, is in the tree, and is
compiled by `npm run build` and exercised by both suites like everything else — not by a test
that compiles generated text. Closing the gap properly means a program built through the
TypeScript compiler API over an in-memory overlay, with `paths` pointed at `packages/src` so
the unbuilt contract resolves. It is worth doing the first time a template change breaks a
generated module; it was not worth doing before that has happened once.

**Products — the decisions worth knowing.**

*A product code is upper-cased and a unit code is not.* Opposite decisions, on purpose. A
catalogue is large, so `widget-1` and `WIDGET-1` is a duplicate nobody notices until stock has
been split across both. A unit list is a handful of rows on one screen, and `kg` is the SI
symbol where `KG` is not — `kWh` means something that neither `KWH` nor `kwh` does, and no
normalisation is right for all three.

*The base unit of a group is the one whose ratio is 1, and no column says so.* Converting is
`amount × from.ratio ÷ to.ratio`, which never names the base — so there is nothing for a
pointer to disagree with. A group is what makes conversion *refusable*: kilograms and grams
convert because somebody said they measure the same thing, and kilograms and hours do not.

*Ratios are `numeric(24, 12)`, twice a quantity's scale.* A quantity is a measurement; a ratio
is a definition. An ounce is 0.028349523125 kilograms exactly, and rounding the definition
would make every weight derived from it permanently and invisibly wrong.

*Deactivating a unit is refused while **active** products are measured in it.* Counting active
products only is what makes the message's advice followable — deactivating those products is
exactly how somebody stops measuring things that way. Both halves are tested.

*A supplier is a party id and nothing else.* No name, no email copied across, so a supplier
corrected in the address book is corrected here by the same act. `PartyDirectory` follows
merges, so linking a duplicate links the record that survived and products never learns a
merge happened. What products deliberately does **not** do is give the party the `supplier`
role: a role is what a party is to the business, parties owns that, and a module reaching
across to write one would be the first crack in "a module may use another's public surface and
nothing else".

*Two migrations, not one.* The generator wrote the module's first; the second turned its single
table into a catalogue. Squashing them would have meant resetting the development database,
which is not a thing to do to somebody's machine for tidiness. The second adds `code` and
`unit_id` as `NOT NULL` without a default, which is only safe because the first creates the
table empty in the same set — true for every database that applies them in order, and true of
no database that will ever exist otherwise.

**What moved for everybody else, because products was the second module to need it.**

- `PartiesModule` is exported from `parties/index.ts` beside `PartyDirectory` — see above.
- `oneOf` and `identifier` are now platform validation rules. Both were copied verbatim from
  parties into products, and the generator emitted a third copy, which is a duplication that
  compounds forty times.
- `exactly` and `defined` are now `backend/src/prisma/columns.ts`. `exactly` matters: it is
  `toFixed()` rather than `toString()`, because decimal.js prints large values in exponential
  notation and `Decimal.parse` refuses an exponent — so `toString()` works on every value
  anybody tests with and loses money on a big one. Products had three of them.
- `narrowed` moved to `@erp/shared` beside `listPath`, and `Select` to `@erp/shared/ui`. Both
  were about to exist twice.
- `Decimal.trimmed()` / `Quantity.trimmed()` are new. Division takes the scale it was told to
  round to whether or not the answer needed it, so 2.5 kg converted to grams was `2500.000000`
  — six digits of precision nobody has, on a number somebody is about to read.

**Left for later, deliberately.**

- **Permissions are declared and nothing checks them.** `products:products:*` and
  `products:units:*` are separate because they are separate jobs — somebody correcting SKUs all
  day should not thereby be able to redefine what a kilogram is. Ticket 07 applies them.
- **No events.** `products.product.created` is the obvious candidate and nobody consumes it.
  Inventory will reach for `ProductCatalogue` because it needs an answer rather than a
  notification.
- **Conversion is contract-only.** `ProductCatalogue.convert` exists and is tested; there is no
  HTTP endpoint for it, because no screen needs one yet. The units screen shows the ratio,
  which is what a person needs in order to check the arithmetic.
- **One cost per product, and no history.** Ticket 13 owns valuation; a cost that changes over
  time is that ticket's problem, and inventing a price list here would be inventing it from
  imagination.
- **There is no way to clear a cost**, only to change one — the same bargain parties struck
  with contact details, for the same reason: an empty box meaning "erase" is also what an
  accidental keystroke means.
